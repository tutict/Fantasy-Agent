## 0. 设计上下文

这一节是 Impeccable 要求的必填项，且必须由人确认——代码只说明建了什么，不说明为谁建、该给人什么感觉。

**2026-10-21 更新：两问都已确认。** 第 1 问「一个人本机操作」，第 2 问「做制图桌吧」。两问的答案互相印证：单人 + 高频重复使用的专业工具，就是一张制图桌，不是一块仪表盘。落到代码上的两件事见 §8.5（左轨折叠）与 §8.6（主按钮归一）。

下面是确认后的状态：

| 项 | 值 | 状态 / 依据 |
|---|---|---|
| 受众 | 游戏策划 / 制作人，**单人在本机操作**一条 prompt→可玩切片的流水线 | ✅ 2026-10-21 工程师确认（原推断依据：`AGENTS.md` 5–15 分钟垂直切片、Studio 只听 `127.0.0.1`） |
| 任务 | 点子访谈 → 计划确认 → 资产/关卡生成 → 试玩 → 返工；中途要在审批闸门前拍板 | 推断：流程控制台 + 编排板 + 策划工作台三个端点 |
| 品牌人格 | 暖纸色 + 氧化铜，克制的工具感，不做游戏 UI 的花哨 | 推断：`tokens.css` 的 `--bg #f3efe6` / `--brand #1f5c52` |
| 一句话差异点 | 它是一张**制图桌**（drafting table），不是一块仪表盘 | ✅ 2026-10-21 确认（原话「做制图桌吧」） |

**「一个人本机操作」实际改变了什么**（写下来，因为它决定了后面每个取舍的方向）：

- **不需要给外人看的解释层。** 受众是一个人且天天用，说明性文案、图例、自解释标签都是纯负担。密度可以往「熟练操作者」的方向压，不用照顾第一次看到它的人。
- **同类控件在不同视图必须一致。** 一个人靠肌肉记忆操作，同一个主按钮在控制台 46px、在设置面板 40px 就是伤害。这条是 `.primary-action` 那笔债该还的理由（§8.4）。
- **5 秒可读性测试的对照方式要改。** 它原本要「三个不熟悉本项目的人」——对一个单人工具，陌生人的第一印象不是有效对照，重复操作下的可扫视性才是。见 §8.4 #2。

**没改变的**：审批闸门仍然必须显眼（一个人用不等于一个人能漏），在飞任务仍然不能因为折叠被卸载。

**「制图桌」实际改变了什么**（这是以后每次取舍的判据，写下来免得它蒸发）：

| 制图桌说的是 | 所以 | 反例（仪表盘会怎么做） |
|---|---|---|
| 一张工作面上摊开工具，你低头干活 | **工作面为主**，面板与 chrome 退到背景 | 指标并列、争做视觉主角 |
| 同一把工具在哪都是同一把 | **同类控件跨视图必须一致**，用 token 不用手调值 | 每个面板按自己需要微调 |
| 工具可预期，靠肌肉记忆 | **尺寸/字重/内距落在既有阶梯上**，不出现 850 这种孤值 | 按视觉需要单独调 |
| 不做花哨 | 状态靠**形状 + 语义色**，不靠亮度或动画抢注意力 | 告警闪烁、渐变、亮色强调 |

**它否决掉的一件事（重要）**：密度预算**不上调一档**。仪表盘方向会要求「多指标并列 → 上限放宽」，制图桌方向相反——工作面要留给内容。`viewDensity.test.tsx` 的四组预算维持 2026-10-21 实测值，不当成可以往上抬的数字。

| 项 | 推断值 | 依据 |
|---|---|---|
| 受众 | 游戏策划 / 制作人，单人在本机操作一条 prompt→可玩切片的流水线 | `AGENTS.md`（5–15 分钟垂直切片）、Studio 只听 `127.0.0.1` |
| 任务 | 点子访谈 → 计划确认 → 资产/关卡生成 → 试玩 → 返工；中途要在审批闸门前拍板 | 流程控制台 + 编排板 + 策划工作台三个端点 |
| 品牌人格 | 暖纸色 + 氧化铜，克制的工具感，不做游戏 UI 的花哨 | `tokens.css` 的 `--bg #f3efe6` / `--brand #1f5c52` |
| 一句话差异点 | 它是一张**制图桌**（drafting table），不是一块仪表盘 | 脚本语言 GUI 克制，卡片阴影只用于对话框 |

**要确认的两件事**（会影响 P1、P3 的具体取值）：
1. 受众是「一个人」还是「要给别人看」？决定编排板/控制台的默认信息量上限。
2. 「制图桌」这个方向对不对？如果偏「仪表盘」，P3 的密度预算要整体上调一档。

## 2. 问题梳理：四个维度

### 2.1 信息层级

**现状**：四张视图各自决定自己显示多少东西，没有任何一处记录「一屏该有多少信息块」。

| 视图 | 结构 | 同屏信息块 |
|---|---|---|
| 流程控制台 | 三栏（左 rail / 中 pane / 右 rail） | **11 个 `<section>`**，右栏叠 `generate-panel`×2 + `rework-panel` + `playtest-panel` + `activity-card` |
| 外壳 | 侧栏 + 主区 | 7 个 `<section>` |
| 编排板 | 单列流式 | 1 个 `<section>`（**唯一有意为之的克制**，`css-conventions.md` §4 记着它不要媒体查询） |
| 资产库 | 整页 | 2 个 `<section>` |

**三个具体病灶**：

| # | 病灶 | 证据 | 后果 |
|---|---|---|---|
| H1 | **主次没有量化** | 控制台右栏 5 个面板等权平铺，`.rail-card` 一视同仁 | 用户分不出该先看哪个；新增面板就是往栈里再塞一块 |
| H2 | **导航/设置在首屏抢位** | 控制台 `top-bar` 里两枚全宽分段控件（语言/主题）排在品牌与计划标题之间（`FlowConsole.tsx:483-507`）；外壳同样问题（`2026-10-19-shell-sidebar-redesign.md` §1 #2） | 首屏最亮的一行是设置，不是内容 |
| H3 | **状态被表达三遍** | 外壳旅程项同时有：编号圆的形状+颜色、`data-state`、文字行（`.nav-state`）（侧边栏计划 §1 #4） | 同一信息三种说法 |

**编排板是反证**：它证明本项目做得出低密度界面。它不是被遗漏，是被有意设计成那样的——所以对控制台的处理应该是「照抄编排板的克制」，不是「发明一套新密度理论」。

### 2.2 布局排版

**核心证据**：51 处 `grid-template-columns`，**26 种不同取值**。

```
repeat(auto-fit, minmax(Npx, 1fr))  →  N ∈ {150, 200, 220, 240, 260}   5 种
minmax(28x, 33x)  系列              →  {284,324} {288,332} 等，相差几十 px
minmax(1xx, 0.4x~0.6fr)             →  {120,0.5} {150,0.6} {160,0.45} {160,0.5}
固定前导列                          →  {20, 40, 64, 288}px
```

**这不只是「数字不统一」，是三类具体后果**：

| # | 后果 | 说明 |
|---|---|---|
| L1 | **视觉上几乎不可区分** | `minmax(284px, 324px)` 与 `minmax(288px, 332px)` 在 1440px 下差不到 10px，但两个面板永不联动：改一个另一个不动，于是「看起来差不多」变成「必须看起来差不多」时无从下手 |
| L2 | **断点行为各自为政** | 5 种 `auto-fit` 阈值意味着 5 个不同的折行点。窄屏下五个面板在 5 个宽度依次塌缩，没有任何一处记录这是有意的 |
| L3 | **响应式心智负担** | 谁想改一个面板的响应式，必须先读懂那 26 种里它用的是哪种，以及为什么 |

**编排板再次是反证**：它 0 个媒体查询、0 个多列 grid，靠 `flex-wrap: wrap` 自然折行。

### 2.3 色彩与字体

**字体：已经在阶梯上，无问题。** 4 档（11/14/16/24），实测 0 种孤值。

**色彩：两套词汇并存，且按文件分裂。**

`tokens.css` 为了让老文件能继续编译，保留了旧名别名：`--accent` = `--brand`、`--danger` = `--status-danger`、`--amber` = `--status-warning`、`--blue` = `--status-running`。实测引用量：

| 词汇 | 总引用 | console | orchestration | studio | workbench | ui | assets |
|---|---|---|---|---|---|---|---|
| **旧名** `--accent`/`--amber`/`--danger`/`--blue` | **119** | 49 | 35 | 15 | 20 | **0** | **0** |
| **语义名** `--status-*` | 40 | 9 | **0** | 12 | **0** | 18 | 1 |

**这是「迁移走了一半停在那里」的典型形态**：`ui.css` 与 `assets.css` 已经全部用语义名，而 console / orchestration / workbench 仍以旧名为主。**没有任何一处记录这个迁移存在、目标是什么、还剩多少**——下一个人改颜色时，他看到的词汇取决于他打开的是哪个文件。

由此产生两个已核实的具体矛盾：

| # | 矛盾 | 证据 |
|---|---|---|
| C1 | **状态色映射有三套独立实现，且取值互相冲突** | ① `ui.css` `.status-badge[data-status="…"]` 映射 **15 个状态到 6 个语义色**，用 `::before` 的形状（圆/方）区分<br>② `console.css` `.review-pill.<state>` / `.task-pill.<state>` 映射 6 个状态（其中 `.review-pill.human` 自己注释着「no longer rendered here」）<br>③ `workbench.css` `.wb-pill.<state>` 映射 2 个状态<br>**冲突实例**：同一个「警告」语义，console 用 `--amber-soft` 做**边框**（`console.css:780-783`），workbench 用 `--amber` **实色**做边框（`workbench.css:597-600`）；同一个「通过」语义，console 用 `--accent`（= brand 绿），`ui.css` 用 `--status-success`。**前者是浅色 vs 实色的差别，在暖纸底上差两个亮度档** |
| C2 | **旧名遮蔽了语义** | `.review-pill.approved` 写 `color: var(--accent)`，而 `--accent` 是 brand 色。读代码的人看到的是「批准 = 品牌色」，看不到「批准 = 成功态」——改品牌色会连带改掉批准态的颜色，而这不是任何人的决定 |

### 2.4 组件样式复用

**这一节是四个维度里最硬的，因为它有 8 条可以直接指到行的证据。**

#### 发现 A：8 个「幽灵类」——TSX 引用了，CSS 里一条规则都没有

```bash
# 复算
grep -rn 'className="rail-card generate-panel"' apps/frontend/src --include=*.tsx
grep -rn "generate-panel" apps/frontend/src/styles/   # 无输出
```

| 类名 | 引用处 | CSS 规则 |
|---|---|---|
| `as-entry-generated` | `assets/parts.tsx:163` | 无 |
| `correction-panel` | `console/FlowConsole.tsx:554` | 无 |
| `generate-panel` | `console/FlowConsole.tsx:729` **与** `:771` | 无 |
| `handoff-panel` | `console/FlowConsole.tsx:514` | 无 |
| `manual-correction-panel` | `console/FlowConsole.tsx:586` | 无 |
| `mcp-status-error` | `studio/StudioShell.tsx:464` | 无 |
| `operator-strip` | `console/FlowConsole.tsx:641` | 无 |
| `spec-status` | `console/rendering.tsx:230` | 无 |

**为什么这是问题，不只是「命名冗余」**：

`cssHygiene.test.ts` 有一条守卫叫「styles the base class a component hangs its modifiers on」，它的注释明确写着：**「A modifier may be aspirational; a base may not」**——修饰类可以暂时没有样式，基类不可以。这 8 个类全部挂在 `rail-card` / `status-chip` / `mcp-status-card` 之后，看起来是「可 aspirational 的修饰类」，但它们**永远不会有样式**：它们的作用是被 JS 或 `aria-label` 选中。

后果有两层：
1. **今天**：`.generate-panel` 被两个**不同**的面板共用（729 行「Run approved asset workers」与 771 行「Generate playable demo」）。哪天有人给它写样式，两个无关面板同时变样——而写代码的人以为自己在改一个。
2. **明天**：类名没有类型系统。读者无法判断 `handoff-panel` 是「有样式的类」「JS 钩子」还是「等待实现的占位」。这 8 个混在第二类里，和真正的第三类没有区别。

#### 发现 B：14 个组件族——同一件事被做了 4 遍

实测后缀相同的类 ≥3 个的族有 14 个，挑最要命的四个：

| 族 | 成员 | 说明 |
|---|---|---|
| `-card` | `.activity-card` `.api-state-card` `.mcp-status-card` `.or-card` `.rail-card` `.stage-card` | 6 种卡片外壳 |
| `-panel` | `.agent-panel` `.api-panel` `.enemy-tuning-panel` `.mcp-panel` `.panel` `.playtest-panel` `.rework-panel` `.wb-panel` | 8 种面板外壳 |
| `-header` | `.api-header` `.as-header` `.journey-header` `.mcp-header` `.pane-section-header` `.spec-bundle-header` `.studio-sidebar-header` | 7 种小节头 |
| `-note` | `.agent-note` `.as-path-note` `.handoff-note` `.or-note` `.studio-side-note` | 5 种提示段落 |

**有些分歧是有意的**（`.journey-header` 是旅程条，本就该和面板头不同），**有些不是**——判断标准不在代码里，在读者脑子里。

#### 发现 C：名字在说谎——`.handoff-note` 是全局的提示段落

```bash
# 复算
grep -rn "handoff-note" apps/frontend/src --include=*.tsx | wc -l
```

实测 **23 处引用，跨 4 个文件**，用在至少 6 个语义上无关的面板：

| 用在哪 | 文案 key | 与 handoff 的关系 |
|---|---|---|
| 计划交接面板 | `handoffHint` | 是本体 |
| 手工修正面板 | `manualCorrectionHint` | 无 |
| 资产执行面板 | `assetExecutionHint` | 无 |
| 生成面板 | `generateHint` | 无 |
| 修正报告卡 ×3 | `correctionNoManifest` 等 | 无 |
| 试玩报告卡 | — | 无 |

**它其实就是 `.hint`**，只是第一个用它的人管它叫 `handoff-note`，后面 22 处沿用。后果：改 `.handoff-note` 的样式会同时改掉 6 个面板，而改的人以为自己在改交接面板。同源的还有 `.handoff-actions`（4 处，含 `PlaytestConfirmBlock`）。

#### 发现 D：一条规则捆 5 个无关选择器

`console.css:239` 把 `.locale-switch` `.theme-switch` `.review-actions` `.handoff-actions` `.mode-grid` 写在同一条 `display:flex` 规则里。**这正是项目自己已经治好过一次的病**：`ui.css` 的焦点环注释写着「a rule that reads as local and is not」——它曾经待在 `console.css` 里，作用于全应用每个字段，只是待在一个名字说不然的文件里。焦点环搬了家，这条没搬。

#### 发现 E：跨表同名守卫存在，但只覆盖一对表，且注册表里有一条失效项

`cssHygiene.test.ts:481` 有一条守卫：**「keeps the shell's two stylesheets from dressing the same class」**，带一个 `KNOWN_SHARED` 注册表。它是 2026-10-19 侧边栏重设计留下的产物，做得对——但两件事需要改：

| 问题 | 实测 |
|---|---|
| **只覆盖 console.css × studio.css 一对** | 全部 7 张表两两组合实测有 **1 处**碰撞（就是已注册的 `.primary-action`）。但另外 6 对表（assets/orchestration/ui/workbench 参与的 15 种组合）**没有任何守卫在看着**。今天没撞，不等于不会撞——而撞的方式是**静默**的：谁赢取决于 Vite 的模块图顺序 |
| **`KNOWN_SHARED` 里 `.mcp-state` 已失效** | 它在 console.css 里只以 `.generate-stages .mcp-state`（后代选择器）形式存在，靠**特异性**取胜而不是导入顺序（守卫自己的注释也这么写），所以按守卫自身的「独立键类」口径它已经不是碰撞。留在注册表里会遮住「这条已经无害了」这个事实 |

## 3. 根因

四个维度收敛到**同一个根因的三个面**：

| 面 | 表述 |
|---|---|

### 5.2 「三处映射」是怎么被证明是低估的

写计划时数出 3 处，靠的是**按名字 grep**：我知道 `data-status`、`data-state`、`data-decision`。扫完以为齐了。

然后每一次换形状扫，都又扫出一批前一次结构上不可能看见的：

| 第几轮 | 扫的形状 | 扫出 | 上一轮为什么看不见 |
|---|---|---|---|
| 1 | `data-status="…"` | 3 处 | — |
| 2 | `[data-*="…"]` 全部属性名 | 6 个属性名、16 条规则 | 前一轮只 grep 了已知名字 |
| 3 | 属性选择器 **＋ 复合类选择器** | 再加 **11 条** | `.wb-chip.ready` 不是属性选择器，形状不同 |

**27 = 16 + 11。** 教训：按名字扫永远扫不出你还没猜到的名字；**按形状扫才扫得完**——映射的形状是「比它所属组件更具体的规则 + 规则体里有颜色」，两个族都符合。

这个教训已经固化成指标了：`ui_metrics.py` 的 `state_mappings_outside_vocabulary` 就是第 3 轮那个扫描，每次跑都重算，**不会再像这张表一样过期**。

### 5.3 `token_coverage_pct` 的 85.6% 本来就是个坏数字

分母里混进了 43 条 `min-height: 28px`、19 条 `max-width`、17 条 `line-height`、67 条 `margin: 0`——**尺寸和重置**，不是装饰。一个 100% 覆盖了错误东西的指标，比一个 85% 覆盖了正确东西的指标更坏。修好 `is_decorative()` 并加了 `is_reset()` 之后，覆盖率自己回到 99.0%，**没有改一行 CSS**。

### 5.4 跨表碰撞：口径改了，两边一起改

扩展守卫时发现旧口径把这三种都算进去了，而它们**都不是**「由导入顺序决定」的碰撞：

```
.review-pill[data-status="human"]  0,2,0 —— 属性选择器自己就赢了
.recovery-actions .ghost-action    0,2,0 —— 后代选择器同理
:where(.review-pill)               0,0,0 —— 故意零特异性，是词汇表列读者的方式
```

所以口径收紧成「**光秃秃的 `.name` 规则**」，`cssHygiene.test.ts` 的 `baseClasses` 和 `ui_metrics.py` 的 `_standalone_in` **同时改**——两边算同一个东西，口径必须一致，否则两套打架的数字比一套坏数字更坏。收窄后 21 对表只剩 1 处真碰撞（`.primary-action`，已带理由注册）。

`.mcp-state` 按新口径自动出注册表了——**不需要手工摘，因为「还在不在撞」现在是每次跑都验的断言**（FE14-3 钉着这条）。

### 8.5 2026-10-21：拿到「一个人本机操作」后做的第一件事

左轨四张卡（交接 / 返工 / 手动修正 / 执行确认）改成**受控折叠**：一次只展开一张，其余三条收成标题栏。

**为什么是折叠而不是不渲染。** 这三张卡里有在飞任务（`useCorrections` 的扫描）和半截输入（返工 textarea）。`<details>` 把 body 留在文档里，两者都活下来；卸载会把它们带走。同一条理由决定了**右轨不折叠**——它 owns 三个轮询 job，`visitedPanels` 的契约是「视图永不卸载」，折叠是唯一会诱使人破坏它的编辑。

**为什么折叠的是左轨。** 左轨是输入与队列（按需），右轨是执行（常驻）。一个人跑流水线时，前者一次只需要一样，后者要一直看得见。

**审批闸门的处理。** `pendingGates > 0` 时 gates 卡强制展开，且折叠状态下标题上挂一个计数徽章（`gate-count`）。折叠绝不能藏起一个待拍板的确认——那是流水线停在一个看不见的原因上。

**实测效果**（`viewDensity.test.tsx`，四视图 × 四轴）：

| 轴 | 折叠前 | 折叠后 | 变化 |
|---|---|---|---|
| 可见文字 | 2286 | **1316** | **−42%** |
| 控件 | 29 | **20** | **−31%** |
| 标题 | 15 | **10** | **−33%** |
| 信息块 | 15 | **15** | 0 |

**信息块没变，这是对的，不是没做成。** 一张折叠起来的卡仍然是一条标题栏，仍然是读者要扫的一行。折叠掉的是 body，而 body 正是另外三个轴在量的东西。要把 15 降下来，得动中栏或右轨——那是下一半，卡在控制台外壳的测试上。

**顺带修好的两个度量 bug**（都是改的时候才发现的）：

1. 守卫原本按 DOM 数节点。折叠后 body 仍在 DOM 里，按 DOM 数等于在量一个读者看不见的屏幕。改成只量**真正呈现出来的**节点（折叠 `<details>` 之下的不算，但其 `<summary>` 算——它是折痕的把手）。
2. 第一版我在每个文本节点后插空格，把相邻文本拆开了，字数虚高（assets 743 → 773）。去掉分隔符后回到原值。

**验证**：typecheck 0；vitest **358/358**（34 → 35 文件）；`ui_metrics.py --check` 0（死类 0、幽灵类 0、token 99.0%）；**变异 4/4 全抓**（FE15-1 针脚随结构搬移、FE16-1 守卫失去折叠感知、FE16-2 卡片被钉开、FE16-3 右轨被折叠），源码 sha256 逐字节还原。

### 8.6 2026-10-21：拿到「制图桌」后做的第一件事——主按钮归一

**跨表碰撞 1 处 → 0 处。** `.primary-action` 是全仓最后一个「两张表给同一个基类各写一份」的类。

之前的两份（三视图共 11 处在用：console 5、orchestration 1、studio 5）：

| | console.css | studio.css |
|---|---|---|
| `min-height` | `var(--size-control)` = 44px | `40px` |
| `font-weight` | `900` | `850` |
| `padding` | 无 | `0 var(--space-3_5)` |
| `font-size` | 继承 | `var(--text-s)` |
| `width` | `100%`（块级） | `auto`（行内） |

**真问题不是重复，是尺寸由导航顺序决定**：两张表都在给同一个基类下定义，谁赢取决于样式表注入顺序——先访问 Studio 再进 Console，Console 的主按钮就是 40px。

**制图桌的判决**：同一把工具在哪都是同一把。合并成一份，放在 `ui.css`（三个视图都渲染它，它是共享组件）。

**保留的差异必须是布局事实，不是漂移。** `width: 100%`（console 块级）vs `auto`（studio 行内）是真实的布局差异，不能并。它走自定义属性 + `:where()`：

```css
/* ui.css —— 唯一定义 */
.primary-action { width: var(--primary-action-width, auto); min-height: var(--size-control); … }

/* console.css —— 只声明布局，:where() 是 0,0,0，不会在导入顺序上打平 */
:where(.primary-action) { --primary-action-width: 100%; }
```

**因此产生的视觉变化**（本机无人眼校验，请自己扫一眼）：studio 侧主按钮 40px → 44px、`font-weight` 850 → 900、`font-size` 统一为 `--text-s`。console 侧无变化（它本来就是 44/900）。`font-size` 统一为 `--text-s` 不是随意挑的——仓库里**其他每一个控件**（`.mode-option` / `.locale-option` / `.tab` …）都用 `--text-s`，只有主按钮在继承正文尺寸，那本身就是漂移。

**守卫侧**：`cssHygiene.test.ts` 的 `KNOWN_SHARED` 注册表清空——它自己在断言「注册了但不再碰撞 → 删掉」，所以条目必须跟着走。新增 `FE17-1` 钉「主按钮不许再长出第二份定义」；`FE14-3` 改钉「注册表里出现失效条目」（这正是 `.mcp-state` 当年的失效方式）。

**验证**：typecheck 0 / vitest **358/358** / `ui_metrics.py --check` 0（**跨表碰撞 0**、死类 0、幽灵类 0、token 99.0%）/ build 0 / **变异 5/5 全抓**，sha256 逐字节还原。
